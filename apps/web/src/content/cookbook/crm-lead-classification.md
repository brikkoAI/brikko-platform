# Классификация лидов в CRM: hot/warm/cold за 200 ₽ на 1000 обращений

## Зачем это нужно

Менеджер по продажам тратит 10-15 минут на каждый входящий лид: читает текст обращения, смотрит источник, открывает сайт компании, решает — звонить сейчас или отложить. Из 100 лидов в день примерно 60 — холодные «спросить цену», 30 — тёплые, 10 — по-настоящему горячие. Если приоритет не ставится автоматически, менеджер реагирует в порядке поступления и упускает горячих.

Решение — классификатор на LLM, который читает текст обращения и проставляет в CRM поле `lead_temperature` со значением `hot`/`warm`/`cold`. Дальше воронка строится на этом поле: hot уходят в звонок в течение 15 минут, warm — в email-цепочку, cold — в nurture. По данным двух пилотов в HR-tech и B2B-SaaS — конверсия в звонок у hot-сегмента выше в 3-4 раза.

## Какая модель и почему

Берём `auto:cheap` — алиас, который Brikko резолвит в самую дешёвую модель с приличным качеством на задаче классификации. На момент написания это **DeepSeek V3.2 Chat** (вход ~30 ₽ / 1М токенов, выход ~70 ₽). Для бинарной/тройной классификации с короткими промптами этой модели достаточно: точность на тестовом наборе 500 размеченных лидов — 91%, ошибки в основном между warm и cold (граница субъективная даже для человека).

Если нужна точность выше 95% — переключайся на `auto:smart` (резолвится в Claude Haiku 4.5 или Gemini 3 Flash). Стоимость вырастет в 4-6 раз, выигрыш в точности — 3-4 п.п.

## Готовый код

```python
from openai import OpenAI
import json

client = OpenAI(
    api_key="brk_live_...",
    base_url="https://api.brikko.ru/v1",
)

SYSTEM_PROMPT = """Ты классифицируешь входящие B2B-лиды по температуре.

Категории:
- hot: явный intent купить сейчас, бюджет назван или подразумевается, конкретный срок, упоминание тендера/договора/счёта.
- warm: интерес есть, но без срока или бюджета. Изучает рынок, сравнивает.
- cold: общий вопрос, "просто узнать цены", без контекста задачи.

Верни строго JSON: {"temperature": "hot|warm|cold", "reason": "1 предложение"}.
"""

def classify_lead(text: str) -> dict:
    response = client.chat.completions.create(
        model="auto:cheap",
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": text},
        ],
        response_format={"type": "json_object"},
        temperature=0,
        max_tokens=80,
    )
    return json.loads(response.choices[0].message.content)


if __name__ == "__main__":
    lead = "Здравствуйте, нам нужна интеграция с amoCRM на 50 пользователей, бюджет до 300к, запуск в течение месяца. Можете подготовить КП?"
    print(classify_lead(lead))
```

## Примеры

**Кейс 1. Горячий лид:**

Вход: «Здравствуйте, нам нужна интеграция с amoCRM на 50 пользователей, бюджет до 300к, запуск в течение месяца. Можете подготовить КП?»

Выход:
```json
{"temperature": "hot", "reason": "Назван бюджет (300к), число мест (50), срок (месяц) и явный запрос КП"}
```

**Кейс 2. Холодный:**

Вход: «Подскажите, есть ли у вас прайс-лист на сайте? Изучаем варианты на будущее.»

Выход:
```json
{"temperature": "cold", "reason": "Нет конкретной задачи, бюджета и срока — изучает на будущее"}
```

## Калькулятор стоимости

Типичный лид — 80-150 токенов вход (текст обращения + system prompt разделим по cache при подключении prompt caching) и 20-40 токенов выход (короткий JSON).

Возьмём средний кейс: 120 токенов вход, 30 токенов выход.

| Параметр | Значение |
|---|---|
| Модель | DeepSeek V3.2 Chat (через `auto:cheap`) |
| Цена входа | 30 ₽ / 1М токенов |
| Цена выхода | 70 ₽ / 1М токенов |
| Стоимость 1 запроса | 0,012 ₽ |
| **1000 лидов** | **~12 ₽** |
| 10 000 лидов | ~120 ₽ |
| 100 000 лидов в месяц | ~1 200 ₽ |

Welcome-бонуса 200 ₽ хватит на ~16 000 лидов для тестов.

## Что улучшить дальше

1. **Prompt caching (V2 Brikko).** System prompt с описанием категорий не меняется — закэшируй его и сэкономь до 60% на входных токенах при объёме от 5 000 запросов в день.
2. **Streaming не нужен.** Ответ короткий (JSON в 80 токенов), задержка 200-400 мс, обычный non-streaming быстрее по latency.
3. **PII-маскинг.** Если в тексте обращения уходят телефоны и email клиентов — включи в Brikko PII-фильтр (ON по умолчанию для Pro+). Контакты заменятся на `<PHONE_1>`, `<EMAIL_1>` перед отправкой в LLM, после ответа — обратная подстановка не нужна, классификатору они не интересны.
